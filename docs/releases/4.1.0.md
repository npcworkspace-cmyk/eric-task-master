# Eric Task Master 4.1.0

Local update prepared on 2026-11-15. Public GitHub releases are not changed by this local delivery.

Task Master is an Agent-neutral execution tool. Batch scripts and persistent ops both use its own selected/default Chrome Profile. Personal host routing does not belong in the product. A host needs a permitted way to execute the CLI on the Task Master computer; a model brand, special provider, MCP service or Agent registration is not required.

## Daily use

Start ops with a goal and an existing/default Profile. No website identity selector or per-action permission table is required for normal work. Open the first URL directly, then use the returned scene for target-based actions. Every completed action group includes its next compact observation, so the Agent need not make separate reserve/get/observe round trips. Large tool-output limits can be handled with small schema sections. UTF-8 JSON files, BOM files and stdin avoid shell-specific quoting.

One task/Profile spans multiple tabs. The Agent reads titles and URLs, selects a unique business page and may read independent tabs concurrently; dependent effects stay ordered. Targeted/global keys, rich-text filling, sequential typing, hover/drag, navigation/history/tab control, file upload, completed download artifacts and viewport screenshots share one action catalog. Unrelated DOM noise no longer invalidates the same document/element. Metadata checks avoid full DOM/layout scans.

Keep the operation and browser scene alive while work is unfinished. A normal action failure returns the scene and original error instead of closing the task. Known non-effect failures are not uncertain external writes. Optional legacy identity envelopes remain strict, but identity discovery/inspection is no longer circular. Definitive task-specific readback can record applied or not-applied results; it does not replay an action or equate an unverified click with business success. The Agent must verify the actual account, target and delivered outcome within the user's task.

## Waiting and host compatibility

`ops listen` waits locally without model requests or empty model-facing heartbeats. An event, stop or explicit timeout returns once; model reasoning after that event has its usual usage. A host capable of waiting or notifying on process completion can keep the Agent attached. Hermes can use its terminal with background execution and completion notification; it uses the same CLI, not a separate browser path. A stopped desktop chat, closed host or sleeping computer is not automatically awakened by the CLI alone.

The existing generic executable/stdin event adapter remains available. The optional Codex adapter is an example, not a Task Master dependency or a claim that every host's lifecycle is identical.

WorkBuddy uses the same Skill and local command/Bash interface. Its Windows shell can invoke the application's bundled Node and CLI entrypoint directly if `.cmd` execution is unavailable. No connector, additional runtime or model-specific browser permission is required. Native shell compatibility and actual model-led completion are reported separately.

## Evidence boundaries

Current local acceptance uses owned isolated Profiles, actual Chrome, the CLI/Manager/worker path, independently counted loopback effects, actual file bytes and retained task state. Native Hermes terminal invocation can be checked without requesting its model. Caller-contract tests do not prove that every model will follow instructions or that every real platform has been validated. Real-account publication, ad spend, domain changes and public release are separate actions requiring their own authorization.

No production dependency, extra model, browser engine or second service is added. The existing Node.js/Playwright/Chrome architecture is retained; site/tab count remains the main browser resource cost. Installer and point-in-time resource measurements belong to the local delivery record, not a universal memory or speed guarantee.
