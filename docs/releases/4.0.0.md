## Why a major version

Task Master 3 established the CLI-first task runtime, with persistent operations introduced in 3.2.0. Version 4 brings those operations together with real online Codex handoff and a complete, same-version runtime/Skill distribution: a task can retain its browser context, accept later commands, wait for conditions and schedules, preserve decisions and action records, and pause for human control.

This is a broader execution model, not a claim that Task Master is a fully autonomous Agent. The Agent still owns strategy, content and business judgment. The local computer and runtime must remain available; host integration is explicit.

## Included in 4.0

- **Two modes:** `batch` for finite work and `operations` for persistent interaction. `auto` selects a mode; prompt-explicit selection applies only to that task. Existing free-form `.mjs` jobs remain supported.
- **Scoped observations and bounded actions:** page-bound references, omission/continuation metadata, small action groups, local condition waits, opt-in screenshots and positive result checks.
- **Human takeover:** a separate mutation pause lock, explicit resume and fresh observation. It is not a third mode and cannot silently change identity or authority.
- **Durable operations:** scoped permissions, prepared/initiated action acknowledgements, confirmed/unknown outcomes, business records and readback reconciliation before any uncertain effect can be retried.
- **Schedules and events:** timezone-aware bounded windows, expiry, misfire policy, run limits and durable pending/delivered/received/handled states. A receipt is never substituted for an Agent decision.
- **Narrow single-send transport:** opt-in protection for known small same-origin JSON POST submissions on explicitly selected Task Master Profiles. Unsupported transport paths are not covered; general exactly-once delivery is not promised.
- **Optional independent online Codex CLI adapter:** event-triggered calls, persistent delivery claims and model-call reservations, interruption limits, allowlisted read-only observation or safe stop, and result verification. No business mutation is supported by this adapter.
- **Operation feedback:** an optional NPC-orange cursor, isolated from normal observations/screenshots, and explicit fresh-scene acknowledgement after safely cancelled native dialogs.

The CLI, local Dashboard, bundled Node.js/Playwright and separate user-state model remain the deployment foundation. Every runtime now also contains `app/scripts/codex-host-adapter.mjs`, its guide and `app/skills/eric-task-master/`. See [Fast operations](https://github.com/npcworkspace-cmyk/eric-task-master/blob/v4.0.0/docs/FAST-OPERATIONS.md) and [the Codex CLI adapter](https://github.com/npcworkspace-cmyk/eric-task-master/blob/v4.0.0/docs/CODEX-HOST-ADAPTER.md) for exact contracts and unsupported cases.

## Browser and authorization boundary

Ordinary scripts use named Task Master-owned stable-Chrome Profiles. Signed-in account administration defaults to the user's selected real local browser through a supported browser-use adapter. That local-browser adapter is not bundled: missing support must result in an explicit choice between connecting the selected browser and authorizing a Task Master Profile for the task, never a silent substitute.

Permissions must specify account, resources, origins, actions and expiry. Page content, scheduled events, mode changes and adapter receipts cannot expand that scope. Stopping a task does not reverse an action already accepted by an external service.

A parent chat waiting during the experiment is not evidence of native host wakeup. Adapter idle calls are separate from parent-chat usage; unobservable token/cost totals are not inferred.

Source acceptance, native installer/portable acceptance and public release verification are separate evidence categories. The local result above is not a substitute for the release's exact-source CI, native-target checks or verification of published assets. These notes do not predeclare those gates successful.

## Upgrade without losing state

1. Locate the existing installation and selected state directory. Do not create a replacement Profile pool when discovery is uncertain.
2. Coordinate with the Owner: finish or explicitly stop active work before replacing the runtime. Native installers refuse an occupied runtime; normal CLI startup does not silently upgrade a compatible Manager.
3. Upgrade the Manager and driving Skill separately. Installing `eric-task-master-skill-v4.0.0.zip` alone does not add 4.0 commands to an older Manager.
4. Preserve Profiles, signed-in browser state, task records and outputs. Application replacement is not permission to delete or merge user state.
5. Confirm Skill metadata, the absolute launcher's `--help` and running `manager status --json` all identify 4.0.0; follow [the installation guide](https://github.com/npcworkspace-cmyk/eric-task-master/blob/v4.0.0/docs/INSTALLERS.md). Use a separately selected state directory for tests.

Historical release assets and existing installations do not upgrade themselves. Continued use of an old download is not prevented by publishing a new Latest release.
