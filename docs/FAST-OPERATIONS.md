# Fast operations

The operations path keeps one existing Task Master task, worker and Chrome context alive across commands. The authorized Agent decides strategy and text; bounded local commands handle mechanical actions, scoped observation and condition waiting. The Manager contains no model. In 4.0.0, an optional, explicitly configured [online Codex CLI host adapter](CODEX-HOST-ADAPTER.md) can start an independent decision Agent using a separately installed and signed-in CLI.

Task Master always uses its own selected or saved default Profile. This is the same browser access model as batch scripts; the product does not route account work to another browser tool. A host's personal tool-selection rules remain outside Task Master. One operation keeps the same Profile and may work across its tabs. Keep it alive while the task is unfinished; an action error returns a diagnostic scene rather than closing the browser. Stop after task completion or explicit cancellation, and pause/retain the scene when user direction is required.

The normal path needs no website account/resource selectors, hand-built permission table or extra preflight. The Agent carries out the authorized task and verifies the visible account/resource and actual result. Explicit website identity/origin/action guards remain available for narrower automation and existing integrations; they are not the default experience.

## Modes and page ownership

There are two execution modes: `batch` (a finite action group and then finish) and `operations` (keep the task waiting for commands/events). A prompt's explicit mode applies to that task and takes precedence without changing saved Profile policy. Otherwise a saved `batch`/`operations` default applies; `auto` consults the declared Skill mode or waiting/follow-up intent, then defaults to a finite batch. `auto` is a selection policy, not an execution engine. Existing one-off scripts remain supported.

Use `taskmaster profiles mode PROFILE --mode auto|batch|operations` to change a saved default. For an individual operation, put `mode` in start input. A Skill can instead declare `skillMode: "operations"` or an explicit waiting/follow-up `intent` under auto selection. Neither a mode change nor page content can expand authorization or switch account/Profile.

`ops takeover` and `ops pause` lock automated mutation while preserving the current browser. They are control states, not an additional execution mode. `ops resume` is explicit; all old target references are invalidated and a fresh observation is required. An in-flight write whose result cannot be confirmed becomes unknown and must be reconciled before continuation.

## Start and continue

Use the selected/default existing Profile within the user's task. Examples do not authorize a real external action. Tests use isolated state and Profiles, not the installed user's active data.

```json
{
  "goal": "Complete the authorized browser task and verify the actual result",
  "mode": "operations"
}
```

```text
taskmaster ops start --profile NAME_OR_ID --goal "Complete the authorized task" --json
taskmaster ops command OP_ID --input @observe.json --json
taskmaster ops command OP_ID --input @actions.json --json
taskmaster ops listen OP_ID --after CURSOR --json
taskmaster ops ack OP_ID --input @receipt.json --json
taskmaster ops decide OP_ID --input @decision.json --json
```

Omit `--profile` to reuse the saved default. Start returns the operation/task IDs and defaults to persistent operations. `ops command` waits up to 30 seconds for the actual worker reply and includes a fresh compact observation after a batch. Use `--wait-ms 0` for the legacy asynchronous reservation, or retrieve a pending reply with `ops get OP_ID --command COMMAND_ID`. Command/action IDs are generated when omitted; return and retain them, especially if delivery is uncertain. Explicit stable IDs keep retries idempotent at the command-reservation boundary; reusing one for changed content is a conflict. A transport failure is not permission to resend with a new ID.

An observation command is `{ "kind":"observe", "payload":{ "maxChars":6000, "maxItems":40 } }`; optional `scope`, `fields`, `offset` and `baselineId` support local reads/expansion/deltas. Each item's `textRange` and `textContinuation` identify omissions precisely. Expand necessary rules/context before deciding. A reference is bound to its document and actual element; unrelated DOM noise does not invalidate an unchanged target, while a new document or replaced element does. Text continuation remains exact-version-bound so changed pages cannot silently splice different source text. Profile-scoped reads do not depend on website selectors. A strict identity guard that is missing/mismatched is reported as `identityStatus` on a diagnostic read; it still blocks guarded external effects and reconciliation. Origin/expiry/revocation constraints remain enforced.

A batch needs only `kind: "batch"` and `payload.actions` (1–16 actions). Page metadata and generated IDs need not be copied by hand after a successful returned observation. Optional group `preconditions` apply before the group; action-level `preconditions` apply before that step; `stopConditions` are checked while executing. Add `expected` and final `verify` conditions for the intended business result. Selectors, exact role/name/text and fresh refs are unique/actionable targets; viewport coordinates support click/hover when a page is visual-only. There is no page-supplied arbitrary-JavaScript interface.

A general session may open its first URL directly and return that scene, without a redundant blank-page observation. A screenshot is also a fresh scene for subsequent visual actions. Manual takeover/resume still requires renewed observation; startup convenience cannot release that lock.

The canonical action list comes from `ops schema`: navigate/back/forward/reload/new-tab/close-tab, click/hover/fill/type/key/select/scroll/drag/upload/download, read/locate/wait. `key` supports characters and combinations, targeted or on the currently focused page. `fill` supports ordinary fields and contenteditable; `text` or `value` conditions read editable text correctly. `type` emits sequential keyboard input. Upload takes explicitly user-authorized absolute file paths, including hidden file inputs. `download` registers its event before clicking and saves the completed file in task artifacts with an `evidenceRef`. These primitives do not grant permission to upload secrets or perform unrelated work.

`tabs` returns page IDs, titles, URLs and selection. `select-tab` accepts a page ID or a unique `title`/`url`/`titleIncludes`/`urlIncludes` and returns that scene. Put `pageId` on individual actions for cross-tab work in one group. Profile-scoped `observe` with up to four `pageIds` reads them concurrently without moving selection; those peer observations use selectors plus pageId, not selected-page refs. An ambiguous tab match stops for the Agent to choose rather than guessing. Dependent effects remain ordered; a new Profile is not needed for each task/tab.

The Manager durably records `prepared` and `initiated` before an effect. A confirmed command without positive checks means the browser primitive completed; `verification.businessResultVerified: false` explicitly prevents equating a click with business delivery. The Agent must inspect/verify the actual result before claiming the task complete. Declared expected/verify failures, lost effect acknowledgement or interrupted submissions preserve `unknown`, block new effects, and never auto-repeat. Diagnostic reads and known non-effect actions remain available. A navigation/preparation failure alone is not an uncertain external write. Errors preserve their original cause, action, phase and target details instead of wrapping away the root failure.

Navigation/history/tab control, hover/scroll/read/wait/download default to non-effect actions. Click/fill/type/key/select/drag/upload are conservatively effect-capable; `effect:false` is for known local preparation, not autosave, submit or a URL that changes server state. A user-authorized task is not blanket permission for unrelated external changes. Profile-bound authorization uses a Profile marker and page URL, not a claim about the actual logged-in website account.

Optional strict identity: supply a legacy `authorization` with real `accountId`, `resourceIds`, `origins`, `allowedActions`, `expiresAt`, plus `identity.account/resource` selectors/attributes. Existing explicit envelopes retain that stricter behavior. Ordinary visible text or real attributes can identify an account/resource; `data-account-id` is merely one fixture example and a generic menu label is never actual account evidence. Strict effects wait briefly for delayed identity elements. You can instead narrow a normal `authorization.scope: "profile"` using origins/actions/URL resources or limits without website selectors. Normal sessions remain authorized until stopped/revoked; an expiry or budget is optional, not an arbitrary new timeout. An explicit expiry pauses effects rather than closing the browser.

Replay protection applies to Task Master's actions, not every browser or website transport retry. In an isolated Chrome 157 diagnostic, one click and one page `fetch` produced three server-side POST effects when the server committed and disconnected before sending response headers. Unknown-state reconciliation prevented additional Task Master actions but could not undo those initial effects. Preserve this negative evidence: count independently observed external effects where possible, do not equate one ledger action with one server submission, and do not claim that non-idempotent external writes are guaranteed exactly once. This limitation does not waive the strict zero-duplicate acceptance gate.

### Opt-in single-send transport for known JSON submissions

For an explicitly selected owned Profile, `ops start` can opt into `singleSendTransport: true`. It is off by default and does not change ordinary scripts or attach to the user's signed-in browser. The guarded operation must know its small same-origin JSON POST request before authorizing an effect. Its effect action declares `transport: { url, method: "POST", bodySha256, maxBodyBytes }`: an exact HTTP(S) URL, the SHA256 of the actual expected request-body bytes, and a positive byte limit no greater than 65536. Do not hash a guessed or differently serialized object, log credential-bearing bodies, or infer endpoint authority from page instructions. This declaration supplements, never replaces, the action's account/resource/origin authorization, original expected result and durable action ID.

The guard matches the request actually emitted by the authorized UI action. It does not manufacture a second business submission. Only after durable `initiated` acknowledgement and current authorization/ownership checks may one exact request be forwarded through Playwright's request transport with `maxRetries: 0` and `maxRedirects: 0`. The single-send allowance is consumed before asynchronous work. Mismatched bodies, extra requests, redirects and transport errors are stopped without a browser-network fallback. Other mutating requests in the guarded operation context are blocked, including late retries after a command ends. A new authorized action requires its own explicit guard; ordinary reads remain available for reconciliation. An already-consumed method/URL/body-digest combination cannot be armed again in the same context, even with a different action ID: this conservative restriction prevents an old retry from using a new action's allowance. A fresh context is not permission to replay an unresolved prior effect.

A disconnect still means `unknown`, not success. Read back the same resource and compare the original expected result before continuing; never replay an uncertain action simply because its guard allowed only one send. Stopping cannot reverse an effect the server already accepted. The original native-transport negative evidence remains valid for unguarded paths.

This is a narrow transport policy, not general exactly-once delivery or universal platform compatibility. It uses Playwright's request transport rather than Chromium's network transport. Service Workers, cross-origin submissions, uploads/streaming, redirects and HTTP-authentication compatibility are outside the supported contract; unsuitable requests must be refused before forwarding. GET/HEAD requests remain on the ordinary path, so a server that mutates state through those methods is not covered. Real-site cookie/CSRF, proxy/TLS and application behavior require separate, explicitly authorized compatibility checks. The isolated three-workflow and fault-injection tests establish only their reported conditions.

Advertising actions preserve before/after, currency, daily/lifetime basis, fields, data range/as-of/attribution and observation window. Page `businessContext` selectors can require exact currency/budget basis and compare action context to observed fields. Configure authorization limits for actual business adjustments (fields, min/max, per-change/cumulative change, age/frequency/daily/cooldown). Website records preserve original values and rollback steps, and keep saved/accepted/propagating/effective distinct. Social records retain community/post/conversation/reply/follow-up identifiers and community rules. The helpers in `operations-workflows.mjs` encode mechanics only; an explicit main-Agent decision supplies content and strategy.

## Local waits, events and evidence

`kind:wait` accepts a bounded `condition` (unique actionable target, exact text/value/attribute, visible/hidden/absent state, or URL), `timeoutMs` and optional `pollMs`. Download waits are supported when registered before the download event; do not assume a late wait proves a prior download. `watch:true` registers up to eight local condition observers, with a `watchId`, event type, deadline and optional one-shot behavior. Watchers read current documents after refresh/navigation; health checks report their checks and last successful observation. Quiet conditions do not generate main-Agent calls. Login/permission conditions, when configured, plus account/context loss and disconnection produce distinct safety events rather than guessed recovery. `wait` with `health:true` returns watcher/page/reference/baseline/listener counts. `cancelWatch` removes a named watcher.

Screenshots are opt-in and default to the current viewport; optionally supply a unique target or validated clip. They are private bounded artifacts, not default model input. Password/email/OTP and `data-private` regions are masked, but other visible data can remain; review before sharing. Observations omit credential-input values, private regions and executable page contents; stored structured data uses the existing redactor. Task-written arbitrary files remain subject to review.

Event lifecycle is pending → delivered → received → handled. A receipt is not a decision. An explicitly configured absolute executable plus argument array can consume bounded JSON on stdin and return an identified accepted delivery receipt. Failed dispatch retains the same pending event for bounded retry. The fixture adapter demonstrates process plumbing only. The optional bundled Codex CLI adapter has separate actual online observe/stop evidence; it does not wake the original desktop conversation or recover an offline host. With no configured supported adapter, events remain available for a live Agent's bounded CLI long poll. Actual host token/cost usage that is unavailable is reported unobservable; character length is not substituted for tokens.

`ops listen` keeps the CLI waiting locally through empty long-poll intervals and prints once a new event arrives, the operation ends, or an optional `--timeout MILLISECONDS` expires. It does not request a model, emit empty heartbeat replies to a model, or mark events handled. A host capable of awaiting the process can leave the Agent attached; a host that times out tool calls and repeatedly resumes inference can still consume tokens. An idle local listener and an idle supported Agent-server process are different from a model repeatedly deciding whether anything changed. The existing generic stdin/executable adapter remains the alternative for hosts that cannot await a process. Do not claim that a CLI process alone wakes a closed desktop chat or sleeping computer.

Every Agent uses the same CLI/schema. Use UTF-8 JSON files with `--input @ABSOLUTE_PATH` or pipe JSON through `--input -` to avoid shell-specific quoting; inline JSON remains optional. Read a small `ops schema --section start|actions|recovery|compatibility --json` section when the host truncates large tool output; unqualified schema still returns the full compatible contract. Non-Codex sessions may set a stable `ERIC_TASK_MASTER_AGENT_ID`; generic CLI callers can read the bundled guide without any Codex installation. An explicit `ERIC_TASK_MASTER_SKILL_DIR` selects that host's installed copy. Host-specific acknowledgement/wait limits must not change actions or browser permissions. A command-execution tool reachable on the Task Master computer is the minimum integration requirement; a remote/cloud terminal does not automatically have access to a desktop installation.

Hermes uses the same commands through its `terminal` tool, not its internal browser tool. For an event wait, run the verified launcher with `ops listen OP_ID --after CURSOR --json` using `background:true, notify:true` (older Hermes versions may call the option `notify_on_complete`). No heartbeat is needed: the process remains quiet and exits with the actual event, allowing Hermes's completion mechanism to resume the Agent. Hermes notifications must be enabled. This uses its normal terminal/process capability, requires no Task Master-specific MCP or model provider, and does not promise wake-up after the Hermes host/computer exits. Actual model reasoning after delivery still uses the selected model's allowance. See [Hermes tools](https://hermes-agent.nousresearch.com/docs/reference/tools-reference) and its [terminal implementation](https://github.com/NousResearch/hermes-agent/blob/main/tools/terminal_tool.py).

WorkBuddy uses the same imported Skill through its command/Bash tool, as supported by its [Skill execution documentation](https://open.workbuddy.cn/en/docs/skill). No connector registration or extra controller is needed for a local installation. Windows shells that do not directly execute `.cmd` can invoke the package's quoted absolute `runtime/node.exe` and `app/src/cli.mjs` paths with the same arguments. JSON file/stdin input avoids quoting differences; preserve IDs and inspect the actual reply/readback. Use the host's available wait/completion capability, without promising closed-chat wake-up or bypassing its command permissions. A native shell invocation verifies the invocation boundary only, not a model-led WorkBuddy business task.

Schedules store UTC instants with an explicit IANA timezone, allowed window, per-window cap, expiry and `once`/`skip` misfire policy. Resume coalesces missed work instead of bursting a backlog. Run/duration/host-call limits are enforced; token/cost enforcement requiring unavailable measurements pauses rather than pretending to enforce spend.

## Recovery and total stop

Read `ops get` and pending events after any disconnect/restart. Never replay an uncertain external effect. `ops reconcile` identifies its original `actionIds` and positively verifies the original results, not unrelated body/html existence. `url` navigates only if the current URL differs; same-URL readback does not reload an asynchronously loading page. `refresh:true` explicitly requests reload. Actual Profile/URL provenance, and strict website identity when configured, must still match. Unresolved/manual conflicts remain unresolved. Resume after takeover requires explicit release and a fresh observation. Interrupted known non-effect actions are recorded failed, not turned into global external-write locks.

General browser actions may have no predetermined `expected` result. Their readback can use explicit task-specific `verify` checks plus an Agent `reason`; do not leave them permanently unrecoverable because a selector was not known in advance. An explained Profile-scoped readback may use the actual application/audit result page or equivalent result checks, while retaining the original action, Profile and configured scope. If actual evidence establishes that an action did **not** take effect, reserve reconciliation with `outcome:"not-applied"`, the reason and positive readback. It records the original action as failed, not falsely successful, and never replays it. A strict identity operation keeps original resource/expected-result binding and additionally requires its recorded before-value for non-application. A missing success message or delayed list alone is not proof of non-application: retain unknown when the outcome cannot be established. Outcome, reason, conditions and original IDs are bound to the reserved decision; a worker cannot substitute another decision.

For an originally recorded HTTP(S) navigation explicitly marked `effect:false`, the recorded resource can describe the source page. Its recovery must read the exact original destination URL, verify the original expected URL condition, and observe the same account plus a currently authorized destination resource. The source identity remains intact and `destinationReadback` records the actual destination separately. This narrow rule cannot be claimed by a new reconcile declaration and does not relax resource matching for external writes or non-navigation preparation.

Use `ops revoke OP_ID`, `ops stop OP_ID` or `ops stop-all`. The last affects operations sessions only, not unrelated script jobs. Existing task/Profile leases and process containment perform shutdown. State/evidence remain available; this does not undo already accepted external actions. Upgrading the installed runtime, replacing existing Profiles or publishing a release requires separate permission.

## Optional cursor and native-dialog acknowledgement

`ops start` accepts optional boolean `showCursor`; operations default on and finite batches default off. An explicit value overrides only that operation and survives recovery, not a Profile preference. Toggle it with `ops update OP_ID --input '{"showCursor":false}' --json` or the checkbox on the existing built-in operation task card. The update reports application only after the worker applies the view preference. It never resumes an operation, releases takeover or authorizes an effect.

The modest orange/white pointer and brief click ripple indicate controlled actions without moving the real OS cursor or focusing a window. Pointer movement is decorative and is not awaited to completion. Exact internally owned overlay nodes are excluded from DOM revision, observations, target references and local watchers; site content is not globally excluded. Normal page/region screenshots temporarily hide the pointer and restore it only if still enabled and active, including failed-capture cleanup. Pause, takeover, tab/navigation cleanup and task completion remove old overlays. Raw free-form Playwright/CDP scripts are not universally tracked. Coordinates come from actual uniquely resolved viewport boxes; iframe helper calibration does not add arbitrary frame-interior targets to the operations protocol.

Unexpected native alert/confirm/prompt is mechanically dismissed, never automatically accepted or supplied secret input. Dismissal leaves `UNEXPECTED_DIALOG`; re-observation, ordinary resume or switching tabs does not clear that safety marker. After judging the current scene, submit a real control command using fresh observation identity/version:

```json
{
  "commandId": "review-dialog-1", "kind": "control",
  "pageId": "FRESH_PAGE_ID", "pageVersion": "FRESH_PAGE_VERSION",
  "payload": { "action": "acknowledge-dialog", "reason": "State the actual reviewed interruption and the decision to continue or refuse" }
}
```

The worker rechecks current origin/account/resource and the Manager durably audits this exact scene before it clears only that page's dialog marker. Any initiated/unknown external effect blocks acknowledgement until genuine same-resource reconciliation. Explicitly non-effect preparation can be abandoned only within the matched scene, never falsely confirmed; other unresolved scene records keep their uncertainty lock. Acknowledgement does not release takeover, clear unrelated unsafe state or retry an interrupted action. A new observation is required afterward. Region screenshots plus parent-page close controls can support the isolated iframe popup case; accepting arbitrary iframe actions or filling a native prompt is not supported by this addition.

## Reproducible local evidence

```text
node scripts/acceptance-fast-operations.mjs ABSOLUTE_OUTPUT_DIRECTORY
node scripts/acceptance-fast-recovery.mjs ABSOLUTE_OUTPUT_DIRECTORY
node scripts/acceptance-cursor-dialog.mjs ABSOLUTE_OUTPUT_DIRECTORY
node scripts/soak-fast-operations.mjs ABSOLUTE_OUTPUT_DIRECTORY
```

`TASKMASTER_FAST_OUTPUT` may select the output directory. Acceptance starts an isolated Manager and Profile plus a loopback stateful fixture and exercises the real CLI → Manager → worker → Chrome → durable ACK path. It covers social reply/follow-up, Google-labelled and Meta-labelled simulated budgets, website save/readback/propagation, scheduled/main-Agent decision continuation, unknown-result protection, modes and page takeover. It never accesses a real social/ad/domain account. Reports, CLI timings, isolated state, fixture state and screenshot artifacts are retained; cleanup success is reported separately.

The legacy `soak-fast-operations.mjs` defaults to 24 actual hours and retains its original `preliminary24HourGatePassed` field for compatibility; it is no longer this round's acceptance gate. It can still exercise deterministic fault coverage with `TASKMASTER_SOAK_DURATION_MS=180000` and `TASKMASTER_SOAK_SAMPLE_MS=5000`. Its short script-driven success is not a live main-Agent decision or a substitute for the user-revised test below.

## 4.0.0 online-host acceptance

One isolated Windows online-host run completed 14,401,755.9 ms with 238 samples and a maximum 61.01-second sample gap. A previously verified scheduled-entry event was reused against unchanged adapter/core hashes, not re-run and not added to the new duration. Two new actual Codex CLI decisions covered a pending event across one failed delivery/reconnection and safe refusal of an unapproved publication request near the end. Both events were handled once; adapter idle model calls and simulator writes were zero. The final minutes observed the safely stopped task, followed by verified isolated cleanup. See the [4.0.0 release record](releases/4.0.0.md) and [adapter guide](CODEX-HOST-ADAPTER.md).

This is bounded read-only online-host evidence, not real-platform writing, original desktop-thread wakeup, all-day stability or universal autonomous completion. Existing unmodified business/safety checks were reused. Ordinary deployment does not need to rerun these engineering experiments.

## Historical optional experiments: two four-hour live lanes

An earlier 2026-11-15 plan proposed two concurrent, separately isolated four-hour experiments. That plan was superseded by critical-risk release acceptance and the single online-host validation above. These scripts remain available for explicitly requested engineering work; they are not the 4.0.0 release gate. Their cancelled or short runs remain incomplete and contribute no duration to the completed online-host run. A future dual-lane claim still requires its own complete reports:

```text
node scripts/acceptance-live-chaos.mjs ABSOLUTE_BUSINESS_LANE_OUTPUT
node scripts/acceptance-live-popups.mjs ABSOLUTE_POPUP_LANE_OUTPUT
```

Each lane has its own Manager state, Profile, loopback fixture, operation/task and seeded plan. Default `TASKMASTER_LIVE_DURATION_MS` is 14,400,000; a 120,000-ms smoke with `TASKMASTER_LIVE_SAMPLE_MS=5000` is intentionally compressed and cannot satisfy the four-hour acceptance gate. Use `TASKMASTER_LIVE_SEED` to reproduce 24 ten-minute slots with seeded 1–6-minute arrival jitter. Each lane's eight families occur three times. One pending challenge per lane is allowed; subsequent slots skipped because of an unresolved request or `HOLD` remain missing coverage, never fabricated successes. Reports identify the current required duration explicitly; the legacy `eightHourGatePassed` field retains its actual eight-hour meaning and stays false for a four-hour run.

The supervisor injects, observes, measures and checks independent fixture outcomes; it does not make semantic choices or create approved root answers. Read `status.json` and `requests/<encoded-challengeId>.json`, inspect compact `ops events` / `ops get OP_ID --command COMMAND_ID` plus needed page evidence, then make actual CLI ack/decide/command/refusal actions. Only after those commands complete, write the request's absolute `decisionPath` with `{schemaVersion:1,challengeId,actor:"root-main-agent",observedAt,decisionAt,summary,disposition,commandIds,eventIds,evidenceRefs}`. Disposition is execute/refuse/defer/stop. The driver requires matching durable handled events, real command receipts and the independent page result; a JSON assertion alone is not success. Windows filenames encode the logical colon-containing challenge ID rather than treating it as a path or alternate stream.

Business challenges exercise change, stale context, insufficient data, uncertainty, login/identity, takeover and declared restart. Popup challenges cover benign overlays, risky consent, destructive confirmations, security challenges, new tabs, iframe parent controls and native alert/confirm/prompt. Native mechanical cancellation is labelled separately from root judgement; root must explicitly review and legally acknowledge the scene before claiming safe continuation. Correct refusal is a safety result, not a claim that login was bypassed or a popup accepted. At least one genuine root decision per family per lane is required. No real account, ad spend, domain configuration or credentials are used.

Keep `run-manifest.json`, append-only `challenges.jsonl`, requests/decisions, observations, `resource-samples.jsonl` and `report.json`. Timestamps distinguish injection, detection, Agent queue, decision, first recovery action, verification and actual resume. Failures and null metrics remain in denominators. The popup lane uses monotonic elapsed time as well as UTC, binds all source `.mjs` files plus package/lock hashes, rechecks those hashes, and rejects unexplained supervision gaps above 120 seconds. A declared restart is a new continuity segment, not an uninterrupted browser session. Source changes require a new evidence segment and root's explicit gate decision.

An output-directory `STOP` file or SIGINT/SIGTERM requests scoped cleanup; `HOLD` stops further injection but keeps monitoring and existing requests visible. Root stays in the current chat to consume both lanes; native closed-Codex wakeup is not claimed. A short smoke, mere process liveness, automatic popup dismissal or an unresolved final request cannot satisfy the dual four-hour gate. Both reports must separately show real duration, required family/root coverage, zero unauthorized/duplicate effects and clean isolated shutdown. Compact receipts may remove repeated serialization, never identity, original expected state, unresolved actions or omission warnings; mechanical helpers cannot choose a semantic response or retry an uncertain effect.

Performance reports compare confirmed same-page mechanical work with the same positive verification, first versus warm phases, median/tail CLI/browser wall time and command round trips. Model calls, actual input/output tokens and reasoning latency remain unobservable in the deterministic test driver. Real platform compatibility, real business outcomes, native closed-host dispatch, installed-runtime validation and publication are separate unverified gates unless their own evidence is supplied.
