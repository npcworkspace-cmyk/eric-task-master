# Eric Task Master

Use the installed or extracted portable `taskmaster` launcher. Normal tasks need no source checkout, installation, registration or extra controller. All work uses Task Master-owned Profiles; reuse the selected or saved default Profile and its tabs. Personal host rules about choosing Task Master versus another browser tool are outside this product. For a new Agent or Skill update, locate the existing application below and verify its absolute launcher with `--help`; update only this Skill when the runtime and live Manager already match it. An Owner-authorized runtime upgrade replaces the application while preserving state: resolve active work below, replace the program and use `manager start --upgrade --json`. Record Skill, launcher and live Manager versions separately; all must be 4.2.1 before calling deployment complete. For a nondefault Skill location, use `ERIC_TASK_MASTER_SKILL_DIR`; if activation reports `not-installed`, import the matching bundled Skill into that Agent. After this Agent reads this file in full, set `ERIC_TASK_MASTER_AGENT_SKILL_VERSION=4.2.1` in its CLI processes. Every non-Codex Agent also sets one stable `ERIC_TASK_MASTER_AGENT_ID` per Agent session, not per command. `AGENT_SKILL_REFRESH_REQUIRED` means read the installed replacement, update that version acknowledgement and retry only a request reported as not executed. Never use another Agent's acknowledgement or assume in-memory instructions updated themselves.

Use `--state-dir ABSOLUTE_DIRECTORY` on every command only when the user requests an isolated data project. Its Manager selects its own port unless `--port` is explicitly supplied. The current Manager and CLI quietly replace an outdated selected installed Skill in the background; each recognized Agent must reload it before starting new work. When an older Manager has active work or occupied Profiles, present the user two choices and wait: finish the work first, or explicitly stop that Manager and its tasks/Profile windows and replace it now. Explain that interrupted or unconfirmed external effects must be checked, never replayed blindly. Only after explicit approval use `manager stop --json` for that selected Manager; otherwise do not force-stop. Runtime upgrade is an explicit Owner action: `manager start --upgrade`; it can consolidate the complete selected Windows legacy state once while retaining its source. Incomplete-view errors require Owner upgrade, not replacement Profiles. Never stop the shared Manager to install or update an Agent Skill alone.

## Run the task

1. Write the smallest useful `.mjs` task for the request. Do not register or install it.
2. Start it once. `run` starts Manager automatically and uses the default Profile:

   ```text
   taskmaster run ./job.mjs --input '@input.json' --detach --json
   ```

3. Retain the returned task ID, run `taskmaster panel --json`, and give the user its fixed Dashboard URL. This only returns the link; run `taskmaster panel` without JSON only when the user asks to open it. Reuse the same panel across tasks.
4. Follow it with `taskmaster follow TASK_ID --json`; optionally add `--wait-ms 30000` to bound a call. Retain `after` and continue with `--after SEQUENCE`. Report meaningful processed counts during a long run.
5. Use `taskmaster files TASK_ID --json` and `files TASK_ID --read RELATIVE_PATH --json` to inspect outputs, following listing/read pagination when truncated. `follow` exits 1 for error/stopped after printing JSON: still read that output and deliver usable partial results. Summarize task state separately from business completion: report evidenced counts, missing work and artifact references, not an assumed success from `finished`. If outputs were cleared or unavailable, say so.

When handing work to another Agent or conversation, retain a secret-free receipt: absolute launcher, explicit state/port selectors if used, task ID, Profile identity, `after`, latest state/progress, pending wait/probe and artifact references. The receiving Agent refreshes `status` and continues `follow --after` for that same task; stale receipt state or `canResume` is not authority to resume, repeat actions or create another task. Report truncated event history as incomplete. No Agent registration is needed.

Use `--profile NAME_OR_ID` only when the user names a Profile. Do not add a preflight check to a normal task. For new-Agent/Skill deployment on Windows, or when PATH or the assumed launcher fails, run the bundled read-only locator (replace `<SKILL_ROOT>` with this Skill folder; optionally pass `-PortableRoot 'KNOWN_EXTRACTION'`):

```powershell
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File '<SKILL_ROOT>/scripts/find-launcher.ps1'
```

It identifies a live Manager's embedded runtime and matching package, then the shared location and installation record before PATH; `%LOCALAPPDATA%\Programs\Eric Task Master` is only a fallback. An unlocatable live Manager is `unresolved`, never permission to select an older launcher. For `found`, verify and use the returned absolute launcher. A failed launcher, `unresolved`, query/permission failure, `MANAGER_STATE_MISMATCH`, `MANAGER_STATE_AMBIGUOUS`, or `MANAGER_LOCATION_INVALID` requires reporting the observed path/error and stopping deployment repair: do not reinstall, edit PATH/registry/configuration, move/delete state, merge data or recreate Profiles. Retain state-error `error.details`, including physical state and identity fingerprints; do not hand-recompute identity. Only `absent` supports a user-requested fresh install. macOS `/usr/local/bin/taskmaster`; Linux `/usr/bin/taskmaster`; otherwise use a known portable launcher. For `DEFAULT_PROFILE_REQUIRED`, ask the user to choose an existing Profile in `taskmaster panel`, including a recovered directory-only Profile, or create one only if none is available.

When the user requests installing or updating to the [Latest Release](https://github.com/npcworkspace-cmyk/eric-task-master/releases/latest), read its tag first. If it is newer than 4.2.1, consult that release's deployment guide, verify its matching assets, replace and activate Manager under the authorized rules above, then load the matching Skill before starting new work; do not use the filenames below for a newer release. If Latest is older than 4.2.1, cannot be verified, or lacks required assets, stop and report rather than downgrade. When no launcher is available, the Windows locator also checks `127.0.0.1:19946` (or `ERIC_TASK_MASTER_PORT`); on other systems check the matching loopback endpoint before installing. Existing installation evidence or an uncertain probe requires reporting the locator error. For confirmed absence and a requested fresh install with Latest `v4.2.1`, obtain matching assets from [v4.2.1](https://github.com/npcworkspace-cmyk/eric-task-master/releases/tag/v4.2.1). Native assets are `eric-task-master-v4.2.1-windows-x64-setup.exe`, `eric-task-master-v4.2.1-macos-<ARCH>.pkg`, or `eric-task-master-v4.2.1-linux-<ARCH>.deb` (ARCH: arm64/x64). If installation fails without changing state, use `eric-task-master-v4.2.1-<TARGET>-portable.zip`, where TARGET is `windows-x64`, `macos-arm64`, `macos-x64`, `linux-x64`, or `linux-arm64`, matching this computer. Verify every downloaded asset against that release's `SHA256SUMS` and read `UNSIGNED-BUILD.txt` before use. Extract portable packages to a permanent folder and use the absolute `eric-task-master/bin/taskmaster.cmd` (Windows) or `eric-task-master/bin/taskmaster` (macOS/Linux) path. Native/portable packages bundle the runtime, Node.js and Playwright; stable Chrome is required. Import the same-version Skill from the application's `app/skills/eric-task-master/`, or the separate `eric-task-master-skill-v4.2.1.zip`: the Skill contains instructions, LICENSE and a read-only locator, not a Manager. Read back deployment versions before claiming 4.2.1 is active. OS security approval may still be required; ZIP does not bypass it.

## Minimal task module

```js
export async function run({ page, context, input, outputDir, progress, wait, signal }) {
  await page.goto(input.url, { waitUntil: 'domcontentloaded' });
  return { processed: 1 };
}
```

The `page` and `context` values are normal Playwright objects. The task decides navigation, selectors, concurrency, retry, pacing, waiting, recovery, and result format. Write valuable output incrementally under `outputDir`; do not wait until the end to persist a large batch. For restartable work, the script atomically saves a secret-free checkpoint with its version/input fingerprint, committed IDs or cursor, pending external effects and next step. The script validates and consumes it; Manager does not interpret business checkpoints. Use `progress()` after meaningful units and generic `wait()` only when this task chooses to pause.

Only the entry `.mjs` is copied and frozen. Keep it self-contained: use Node built-ins, bare `playwright`, task `input`, absolute paths, or `outputDir`. Relative sibling imports/files are not copied. For uncertain submission retries, optionally use `run --request-key KEY` (1-160 ASCII letters/digits/`._:-`, starting with a letter/digit): identical submissions return the same task; changed content requires a new key. This prevents duplicate submission, not duplicate business actions. After `MANAGER_RESTARTED`, the old Worker cannot resume and original input is not retained. Read partial outputs first; only explicitly start a new attempt with a compatible script/checkpoint, freshly supplied authorized input and a distinct attempt key when continuation is safe.

For errors, inspect `status`/`follow` error details, last progress and nullable `task.failureScreenshot`. When present, it is an artifact-relative hint: confirm it through `files`, decode base64 if returned, and inspect locally; it is not a filesystem path or proof of the current page. For older Managers or a missing reference, inspect the artifact listing; do not assume a screenshot exists. If an external effect has an unknown outcome, inspect the page/service before repeating it; if still uncertain, stop and ask. Never put cookies, tokens, passwords or authorization headers in progress, outputs, checkpoints or handoff receipts. Artifacts are raw task-written bytes, not automatically redacted; review files and screenshots before sharing.

## Verification waits

When the task detects a verification page, stop dispatching work and call `await wait({ reason: 'verification' })`. If it is in another tab, pass `page: thatPage`. Detection belongs to the task; Manager does not intercept arbitrary raw scripts. Do not add a screenshot timer to the task.

Manager retains Chrome, Worker and heartbeat, freezes execution timeout, and requests a system notification immediately and every 30 seconds until actual resume or the 20-minute deadline. Page screenshots occur at 5/10/15/20 minutes. Before the deadline, `follow` returns screenshot `attention` and an `after` cursor. Open `attention.screenshotPath`; only if clearly recovered, run `taskmaster resume TASK_ID --probe PROBE_ID --json` with `attention.probeId`. Otherwise continue following with `--after SEQUENCE`; uncertainty means stay waiting.

At 20 minutes Manager automatically pauses and stops reminders, preserving the browser and checkpoint. `follow` returns `manualResumeRequired`; the final screenshot is diagnostic only and must not trigger probe-based resume. The Dashboard Resume button or user's resume request maps to `taskmaster resume TASK_ID --json`. `stop`/`delete` cancel reminders and end the task. Keep following before automatic pause: CLI cannot wake an Agent whose turn or terminal session ended. Any later wakeup belongs to a supported, user-authorized Agent-host mechanism, not Manager; otherwise hand off the receipt without promising automatic continuation. Notification presentation follows OS settings; failures never block task control.

## Fast operations and modes

Only `batch` and `operations` execute work; `auto` selects a mode and takeover is a pause lock. Use scripts for known repeated paths and ops for interactive decisions/follow-up. Prompt mode overrides the Profile default for that task only.

Start: `ops start --profile NAME_OR_ID --goal "Authorized task" --json`; omit `--profile` to reuse the saved default. Normal operations have batch-like Profile access, with no required website identity selectors, resource IDs or action allowlists. The Agent still checks the actual website login/target. Explicit legacy account authorization stays a strict optional guard; never invent data attributes or use a generic menu label as account identity.

Read `ops schema --section actions --json` for the common action catalog; other small sections are `start`, `recovery` and `compatibility`, and unqualified schema retains the full contract. Every Agent uses the same JSON. UTF-8 (including BOM) `--input @ABSOLUTE_FILE` or `--input -` via stdin avoids shell quoting differences. Generic hosts can read the bundled guide without any Codex installation; `ERIC_TASK_MASTER_SKILL_DIR` selects that host's installed copy, not another Agent's directory.

Open the initial URL directly with one navigate action, or observe an existing scene before target-based actions. Send `kind:batch` with `payload.actions`. Generated command/action IDs and optional scene metadata remove manual copying. A command waits up to 30 seconds and returns its reply plus the next compact observation. Use `--wait-ms 0` for asynchronous reservation and `ops get OP_ID --command COMMAND_ID` for a pending result; do not infer success from CLI exit code alone.

For successive interactive decisions, keep `ops stream OP_ID --json` open in the host's persistent process facility. Send one normal command JSON line, read its reply, inspect it, then send the next line; the Manager and selected guide are rechecked for every submitted line. This saves repeated CLI startup without changing permissions or execution. Closing stdin ends only that CLI, not the operation or browser. A changed Manager/guide or lost response ends the stream; inspect the original command/action IDs before reconnecting, and never automatically replay an uncertain effect. Hosts without persistent stdin can continue using ordinary `ops command`. See `app/docs/OPERATIONS-STREAM.md` for framing and error details.

Replies default to a small decision view: current status/scene, fresh `ref`, role/name, safe values, meaningful state, warnings and explicit omissions. Repeated ancestor text and private selector paths are not repeated on the wire. Use `ref` directly for the next action; do not require a CSS selector when a fresh ref is supplied. A missing optional false/default field is not a missing control, and omitted context is not evidence of absence. Read `ops schema --section output --json` when adapting a client.

Healthy success replies omit repeated route IDs, ID-only successful action rows, timings and empty control defaults. Missing verification never means business verified; missing default identityStatus never means website-account-verified. Keep commandId and the known operation route for exact full reads. If retaining the same-scope scene, explicitly copy its baselineId into the next observe payload or batch observation options; apply delta items/removed refs, but reset on baselineReset/page/document change. Partial captures cannot prove removals. Never silently change a replayed command envelope to obtain a different delta.

Request the exact stored receipt with `ops get OP_ID --command COMMAND_ID --detail full --json`, or the complete audit with `ops get OP_ID --detail full --json`. `--detail full` changes only the response view: it never replays the command or recaptures a past page. A fresh browser read uses `kind:observe` with `payload.detail:"full"`, optionally `ref:REF` or a unique `scope`. Replay returned continuation options exactly, including offsets, textMode and page/version bindings; own-text and full ancestor text are different source bases. Use the returned fullEvidence/fullReceipt pointer for omitted history or `OUTPUT_CONTEXT_INSUFFICIENT`; its original command status still applies and does not authorize a new submission.

Reuse the scene already returned after each action. Group consecutive known, authorized steps with preconditions in one batch; stop to inspect genuinely new menus, notices, account/resource context or confirmation content. Do not add an unused observe between every action, or expand all history merely to find the last result. A normal get/stop receipt deliberately does not repeat every past command. `COMMAND_RECEIPT_UNAVAILABLE` retains the original outcome but means stored evidence is unreadable: stop automation, require Owner state/evidence recovery, and never replay; unlike formatting overflow it has no usable full-receipt link. Detailed output and screenshots remain available on demand. See `app/docs/OPERATIONS-OUTPUT.md` for the compact/full contract.

Reuse the operation/Profile across tabs: `tabs` returns titles/URLs; `select-tab` uniquely matches pageId/title/URL and returns that scene. Actions may specify `pageId`; observe `pageIds` reads up to four tabs concurrently using selectors plus pageId. Never create a Profile per tab/task. Keep dependent writes ordered.

Primitives: click/hover/fill/type/key/select/scroll/drag, navigation/history/tab controls, upload/download and read/wait. `fill` and text/value readback support contenteditable, included in default observations. `key` without a target uses the focused page. Screenshot defaults to the viewport; download saves an artifact. Expand omitted context/rules via returned text ranges before deciding.

Supply `expected`/`verify` for actual delivery: primitive completion alone is not proof of a posted comment or saved setting. `effect:false` is for known local preparation, not autosave/submission. Preserve IDs: unknown effects require actual-result `reconcile`, never a new ID/retry. An explained, positively checked `outcome:not-applied` can record a definite non-application as failed; absence of a success message alone is not proof. Inspection and known non-effect actions remain usable. Same-URL readback does not reload unless `refresh:true`.

Conditions use AND across supplied URL/state/content predicates; unsupported keys/types reject before actions. Use checked for actual checkbox/ARIA state and values for the entire multi-select collection. expectedMatched/groupMatched report checks actually performed, not automatic business proof. A fresh ref follows the same connected node through reordering and supports exact post-fill readback; a replaced/detached target stops rather than clicking a substitute.

Keep the session/scene alive while work is unfinished. Stop only after completion or explicit cancellation; pause and retain the scene if user direction is needed. `takeover`/`pause` never auto-resume.

Use `ops listen OP_ID --after CURSOR --json` for local waiting with no empty model-facing output; ack/decide the delivered event. The listener makes no model calls. A host that repeatedly resumes inference can still spend tokens; a process alone cannot wake a closed host/original desktop chat. Existing executable/stdin-JSON adapters are shared across hosts. The optional Codex decision adapter is documented in `app/docs/CODEX-HOST-ADAPTER.md`; do not promise untested host wake-up or real-site compatibility.

For Hermes, use its normal terminal for CLI calls; wait through `terminal` with `background:true, notify:true` and the same `ops listen` command (older versions name the option `notify_on_complete`). Leave heartbeat off. Enabled host notifications deliver completion with the event, without model polling; a remote terminal must have an explicit path to the Task Master computer. Do not replace this with Hermes's own browser or a new Profile per business tab.

For WorkBuddy, import this same Skill and use its command/Bash tool with the installed application, not a separate browser or connector. On Windows, if that shell cannot execute `.cmd` directly, use the package's quoted absolute `runtime/node.exe` and `app/src/cli.mjs` paths followed by the same CLI arguments; no extra Node installation is needed. Send JSON by file/stdin and keep the same operation/task IDs. Use the host's supported wait/completion facility for `ops listen`; do not assume a background process can wake a closed chat. Respect the host's own command approvals.

## Control

Use `taskmaster status TASK_ID --json`, `taskmaster stop TASK_ID --json`, `taskmaster resume TASK_ID --json` or `taskmaster delete TASK_ID --json`. Resume requires a live waiting Worker; it does not restart a dead script. Built-in operations support optional `showCursor` (operations on, batch off) and a view-only Tasks switch; normal observations/screenshots exclude that cue. After a native dialog is mechanically cancelled, use the fresh-scene `control` action `acknowledge-dialog` with an explicit reason, as defined by `ops schema --json`; never substitute unrelated action reconciliation or use acknowledgement to bypass an unknown external effect or takeover lock.

Manager owns browser startup, one-writer Profile leases, process cleanup, and task persistence. The task module owns the work. For known small same-origin JSON POSTs in an explicitly selected Profile, consult `ops schema --json`: `singleSendTransport:true` plus each effect's exact endpoint/body-digest guard permits one matching send, blocks other/late writes, and rejects reused digests in that context. Its different transport has explicit compatibility exclusions; never bypass a refusal through unguarded fallback or replay an unknown effect in a new context. Native browser/site retries remain possible outside this opt-in policy: one ledger action is not proof of one external submission, and exactly-once is not promised. For manual sign-in, open the Profile in the Dashboard or with `taskmaster profiles open NAME_OR_ID`: this is native Chrome without a debugging connection. Close all its windows before starting a task. Automation reuses that same Profile; individual sites can still require verification again.
