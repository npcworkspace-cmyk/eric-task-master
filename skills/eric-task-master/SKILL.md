# Eric Task Master

Use the installed or extracted portable `taskmaster` launcher. For a normal request, do not inspect the project source or create another controller. For a new Agent or Skill update, locate the existing application as below and verify its absolute launcher with `--help`; install/update only this Skill when the runtime and live Manager already match it. An Owner-authorized runtime upgrade is a replacement, not a second installation: resolve active work as below, preserve state, replace the application, and run the new absolute launcher with `manager start --upgrade --json` to activate the Manager and synchronize the installed driving Skill. Record Skill metadata, launcher and live Manager versions separately; all must be 4.0.2 before calling this deployment complete. If the response says `not-installed`, import the bundled same-version Skill into the selected Agent. For a nondefault Skill location, set `ERIC_TASK_MASTER_SKILL_DIR` to its absolute `eric-task-master` folder for activation and subsequent commands. An old Agent host may retain a stale PATH; use the verified absolute launcher. Account backends use the user's selected signed-in local browser through available `local-browser-admin` by default; do not silently substitute a Profile, copy credentials or attach through an unsupported connection. If browser/account/authority is unclear, offer two explicit choices and await selection. After this Agent has read the installed `SKILL.md` in full, set `ERIC_TASK_MASTER_AGENT_SKILL_VERSION=4.0.2` in each Task Master CLI process it launches. For a non-Codex Agent host, also set `ERIC_TASK_MASTER_AGENT_ID` to a stable identifier unique to that Agent session. If the CLI reports `AGENT_SKILL_REFRESH_REQUIRED`, quietly read the newly installed Skill in full, set the version from its metadata, and retry only the request explicitly reported as not executed. This acknowledgement is per Agent process; do not copy a different Agent's acknowledgement or assume an old in-memory Skill refreshed itself.

Use `--state-dir ABSOLUTE_DIRECTORY` on every command only when the user requests an isolated data project. Its Manager selects its own port unless `--port` is explicitly supplied. The current Manager and CLI quietly replace an outdated selected installed Skill in the background; each recognized Agent must reload it before starting new work. When an older Manager has active work or occupied Profiles, present the user two choices and wait: finish the work first, or explicitly stop that Manager and its tasks/Profile windows and replace it now. Explain that interrupted or unconfirmed external effects must be checked, never replayed blindly. Only after explicit approval use `manager stop --json` for that selected Manager; otherwise do not force-stop. Runtime upgrade is an explicit Owner action: `manager start --upgrade`; it can consolidate the complete selected Windows legacy state once while retaining its source. Incomplete-view errors require Owner upgrade, not replacement Profiles. Never stop the shared Manager to install or update an Agent Skill alone.

## Run the task

1. Write the smallest useful `.mjs` task for the request. Do not register or install it.
2. Start it once. `run` starts Manager automatically and uses the default Profile:

   ```text
   taskmaster run ./job.mjs --input '@input.json' --detach --json
   ```

3. Retain the returned task ID, run `taskmaster panel --json`, and give the user its fixed Dashboard URL. This only returns the link; run `taskmaster panel` without JSON only when the user asks to open it. Reuse the same panel across tasks.
4. Follow it with `taskmaster follow TASK_ID --json`; optionally add `--wait-ms 30000` to bound a call. Retain `after` and continue with `--after SEQUENCE`. Report meaningful processed counts during a long run.
5. Use `taskmaster files TASK_ID --json` and `files TASK_ID --read RELATIVE_PATH --json` to inspect outputs, following listing/read pagination when truncated. `follow` exits 1 for error/stopped after printing JSON: still read that output and deliver usable partial results. Summarize task state separately from business completion: report evidenced counts, missing work and artifact references, not an assumed success from `finished`. If outputs were cleared or unavailable, say so.

When handing work to another Agent or conversation, retain a secret-free receipt: absolute launcher, explicit state/port selectors if used, task ID, Profile identity, `after`, latest state/progress, pending wait/probe and artifact references. The receiving Agent refreshes `status` and continues `follow --after` for that same task; stale receipt state or `canResume` is not authority to resume, repeat actions or create another task. Report truncated event history as incomplete. No Agent registration is needed.

Use `--profile NAME_OR_ID` only when the user names a Profile. Do not add a preflight check to a normal task. For new-Agent/Skill deployment on Windows, or when PATH or the assumed launcher fails, run the bundled read-only locator (replace `<SKILL_ROOT>` with this Skill folder; optionally pass `-PortableRoot 'KNOWN_EXTRACTION'`):

```powershell
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File '<SKILL_ROOT>/scripts/find-launcher.ps1'
```

It identifies a live Manager's embedded runtime and matching package, then the shared location and installation record before PATH; `%LOCALAPPDATA%\Programs\Eric Task Master` is only a fallback. An unlocatable live Manager is `unresolved`, never permission to select an older launcher. For `found`, verify and use the returned absolute launcher. A failed launcher, `unresolved`, query/permission failure, `MANAGER_STATE_MISMATCH`, `MANAGER_STATE_AMBIGUOUS`, or `MANAGER_LOCATION_INVALID` requires reporting the observed path/error and stopping deployment repair: do not reinstall, edit PATH/registry/configuration, move/delete state, merge data or recreate Profiles. Retain state-error `error.details`, including physical state and identity fingerprints; do not hand-recompute identity. Only `absent` supports a user-requested fresh install. macOS `/usr/local/bin/taskmaster`; Linux `/usr/bin/taskmaster`; otherwise use a known portable launcher. For `DEFAULT_PROFILE_REQUIRED`, ask the user to choose an existing Profile in `taskmaster panel`, including a recovered directory-only Profile, or create one only if none is available.

When the user requests installing or updating to the [Latest Release](https://github.com/npcworkspace-cmyk/eric-task-master/releases/latest), read its tag first. If it is newer than 4.0.2, consult that release's deployment guide, verify its matching assets, replace and activate Manager under the authorized rules above, then load the matching Skill before starting new work; do not use the filenames below for a newer release. If Latest is older than 4.0.2, cannot be verified, or lacks required assets, stop and report rather than downgrade. When no launcher is available, the Windows locator also checks `127.0.0.1:19946` (or `ERIC_TASK_MASTER_PORT`); on other systems check the matching loopback endpoint before installing. Existing installation evidence or an uncertain probe requires reporting the locator error. For confirmed absence and a requested fresh install with Latest `v4.0.2`, obtain matching assets from [v4.0.2](https://github.com/npcworkspace-cmyk/eric-task-master/releases/tag/v4.0.2). Native assets are `eric-task-master-v4.0.2-windows-x64-setup.exe`, `eric-task-master-v4.0.2-macos-<ARCH>.pkg`, or `eric-task-master-v4.0.2-linux-<ARCH>.deb` (ARCH: arm64/x64). If installation fails without changing state, use `eric-task-master-v4.0.2-<TARGET>-portable.zip`, where TARGET is `windows-x64`, `macos-arm64`, `macos-x64`, `linux-x64`, or `linux-arm64`, matching this computer. Verify every downloaded asset against that release's `SHA256SUMS` and read `UNSIGNED-BUILD.txt` before use. Extract portable packages to a permanent folder and use the absolute `eric-task-master/bin/taskmaster.cmd` (Windows) or `eric-task-master/bin/taskmaster` (macOS/Linux) path. Native/portable packages bundle the runtime, Node.js and Playwright; stable Chrome is required. Import the same-version Skill from the application's `app/skills/eric-task-master/`, or the separate `eric-task-master-skill-v4.0.2.zip`: the Skill contains instructions, LICENSE and a read-only locator, not a Manager. Read back deployment versions before claiming 4.0.2 is active. OS security approval may still be required; ZIP does not bypass it.

## Minimal task module

```js
export async function run({ page, context, input, outputDir, progress, wait, signal }) {
  await page.goto(input.url, { waitUntil: 'domcontentloaded' });
  return { processed: 1 };
}
```

The `page` and `context` values are normal Playwright objects. The task decides navigation, selectors, concurrency, retry, pacing, waiting, recovery, and result format. Write valuable output incrementally under `outputDir`; do not wait until the end to persist a large batch. For restartable work, the script atomically saves a secret-free checkpoint with its version/input fingerprint, committed IDs or cursor, pending external effects and next step. The script validates and consumes it; Manager does not interpret business checkpoints. Use `progress()` after meaningful units and generic `wait()` only when this task chooses to pause.

Only the entry `.mjs` is copied and frozen. Keep it self-contained: use Node built-ins, bare `playwright`, task `input`, absolute paths, or `outputDir`. Relative sibling imports/files are not copied. For uncertain submission retries, optionally use `run --request-key KEY` (1-160 ASCII letters/digits/`._:-`, starting with a letter/digit): identical submissions return the same task; changed content requires a new key. This prevents duplicate submission, not duplicate business actions. After `MANAGER_RESTARTED`, the old Worker cannot resume and original input is not retained. Read partial outputs first; only explicitly start a new attempt with a compatible script/checkpoint, freshly supplied authorized input and a distinct attempt key when continuation is safe.

For errors, inspect `status`/`follow` error details, last progress and nullable `task.failureScreenshot`. When present, it is an artifact-relative hint: confirm it through `files`, decode base64 if returned, and inspect locally; it is not a filesystem path or proof of the current page. For older Managers or a missing reference, inspect the artifact listing; do not assume a screenshot exists. If an external effect has an unknown outcome, inspect the page/service before repeating it; if still uncertain, stop and ask. Never put cookies, tokens, passwords or authorization headers in progress, outputs, checkpoints or handoff receipts. Artifacts are raw task-written bytes, not automatically redacted; review files and screenshots before sharing.

## Verification waits

When the task detects a verification page, stop dispatching work and call `await wait({ reason: 'verification' })`. If it is in another tab, pass `page: thatPage`. Detection belongs to the task; Manager does not intercept arbitrary raw scripts. Do not add a screenshot timer to the task.

Manager retains Chrome, Worker and heartbeat, freezes execution timeout, and requests a system notification immediately and every 30 seconds until actual resume or the 20-minute deadline. Page screenshots occur at 5/10/15/20 minutes. Before the deadline, `follow` returns screenshot `attention` and an `after` cursor. Open `attention.screenshotPath`; only if clearly recovered, run `taskmaster resume TASK_ID --probe PROBE_ID --json` with `attention.probeId`. Otherwise continue following with `--after SEQUENCE`; uncertainty means stay waiting.

At 20 minutes Manager automatically pauses and stops reminders, preserving the browser and checkpoint. `follow` returns `manualResumeRequired`; the final screenshot is diagnostic only and must not trigger probe-based resume. The Dashboard Resume button or user's resume request maps to `taskmaster resume TASK_ID --json`. `stop`/`delete` cancel reminders and end the task. Keep following before automatic pause: CLI cannot wake an Agent whose turn or terminal session ended. Any later wakeup belongs to a supported, user-authorized Agent-host mechanism, not Manager; otherwise hand off the receipt without promising automatic continuation. Notification presentation follows OS settings; failures never block task control.

## Fast operations and modes

Only `batch` and `operations` execute work: use bounded batches for known repeated mechanical paths, and persistent operations for long follow-up with several main-Agent decisions. Prompt-selected `mode` wins for this task without rewriting Profile defaults; otherwise use Profile `modePolicy`, or `auto` with explicit `skillMode`/waiting or follow-up intent, then finite `batch`. Use `profiles mode NAME_OR_ID --mode auto|batch|operations` only to change the saved default. First read `ops schema --json` for the complete offline contract and copyable payloads; no source checkout or website is needed. `ops start --input @start.json` requires selected browser, scoped unexpired account/resource/origin/action authorization and actual account plus resource selectors. Reuse returned operation/task IDs: `ops command OP_ID --input @command.json`, then compact `ops get OP_ID --command COMMAND_ID` for that reply and safety state; reserve full `ops get OP_ID` for reconciliation. Observe fresh pageId/pageVersion before a batch with preconditions/stop conditions/positive verification. Omitted text has explicit text ranges and scoped textOffset continuation: expand required rules/context before deciding. Use `ops events OP_ID --after CURSOR --wait-ms 30000`, `ops ack` and `ops decide` for main-Agent decisions; local waits need no model polling. `ops takeover`/`pause` are page-control locks, never a third mode; explicit resume requires fresh observation. Unknown writes require identity-bound read-only `ops reconcile` against the original effects, never replay. `ops revoke`, `stop` and `stop-all` cancel scoped operations. Optional online Codex CLI decisions use the application's `app/scripts/codex-host-adapter.mjs`; first read `app/docs/CODEX-HOST-ADAPTER.md`, then supply an explicit absolute `--config` and the stdin `hostAdapter` contract. It uses its own authenticated CLI, at most three persistent model-call slots, and only `observe`/`stop`; it cannot wake the original desktop chat, a sleeping/offline computer or a closed host. A received event is not a handled decision; require verified receipts. Pending events or notifications do not prove automatic wakeup. Isolated simulation does not prove real-platform support.

## Control

Use `taskmaster status TASK_ID --json`, `taskmaster stop TASK_ID --json`, `taskmaster resume TASK_ID --json` or `taskmaster delete TASK_ID --json`. Resume requires a live waiting Worker; it does not restart a dead script. Built-in operations support optional `showCursor` (operations on, batch off) and a view-only Tasks switch; normal observations/screenshots exclude that cue. After a native dialog is mechanically cancelled, use the fresh-scene `control` action `acknowledge-dialog` with an explicit reason, as defined by `ops schema --json`; never substitute unrelated action reconciliation or use acknowledgement to bypass an unknown external effect or takeover lock.

Manager owns browser startup, one-writer Profile leases, process cleanup, and task persistence. The task module owns the work. For known small same-origin JSON POSTs in an explicitly selected Profile, consult `ops schema --json`: `singleSendTransport:true` plus each effect's exact endpoint/body-digest guard permits one matching send, blocks other/late writes, and rejects reused digests in that context. Its different transport has explicit compatibility exclusions; never bypass a refusal through unguarded fallback or replay an unknown effect in a new context. Native browser/site retries remain possible outside this opt-in policy: one ledger action is not proof of one external submission, and exactly-once is not promised. For manual sign-in, open the Profile in the Dashboard or with `taskmaster profiles open NAME_OR_ID`: this is native Chrome without a debugging connection. Close all its windows before starting a task. Automation reuses that same Profile; individual sites can still require verification again.
